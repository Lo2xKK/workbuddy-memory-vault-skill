# 设计论述：为什么要「编译」对话，以及怎么编译

> 本文回答的是 **为什么**：为什么需要这个工具、为什么这样设计、取舍在哪里。
> **怎么用**请看 [README](../README.md)——它承担「30 秒判断 + 5 分钟上手」的门面职责。
>
> 本文出现的产物片段，均由 `scripts/render.py` 的渲染函数对**合成输入**实际渲染得到（内容为中性示例）。
> 它们不是手写的示意图，也不是真实对话内容——对象结构、字段顺序、链接写法都与实际产物一致。

---

## 一、问题：对话资产的三重困境

我们每天在 AI 对话里做的判断、踩过的坑、定下的方案，数量已经远超能记住的限度。但这些资产在当下的形态里几乎不可用，原因有三个，且互相叠加。

### 困境一：找不到

问题不在「没记录」，而在「记录躺在不会被翻第二次的地方」。一条几十轮的对话，真正有价值的部分可能只有三百字——一个参数为什么这么填、一个报错最后怎么绕过去。而它被埋在一个按时间排列的会话列表里，标题是自动生成的、只描述了开头三句话。

你周二解决了一个难题，三个月后在另一个项目里从头解决一遍。这不是记性问题，是检索问题。

### 困境二：不可迁移

WorkBuddy 是少数把会话**落到本地**的 agent——`~/.workbuddy/projects/<workspace>/<session-id>.jsonl` 是明文记录，会话标题在本地 SQLite（`workbuddy.db` 的 `sessions` 表）里。这已经比绝大多数同类产品走得远。

但「本地有文件」和「你能用它」是两回事。jsonl 是**给程序看的中间格式**：每轮助手回复被切成多个 `message` 片段（每次工具调用前后各一段），中间夹着 `function_call`、`function_call_result`、`reasoning` 与文件快照。直接打开它，读到的是碎片，不是对话。

### 困境三：不可检索

即便你忍着手工翻 jsonl，也拿不到检索能力：这不是纯文本，`grep` 能命中字符串但给不出上下文；装了插件也进不了任何笔记系统；换一台机器、换一个工具，一切归零。

**量化的落差**：某次真实试跑中，43 MB 原始数据里，剥掉工具返回（16.5 MB）、工具参数（9.4 MB）、推理过程（3.9 MB）与文件快照（1.6 MB）之后，真正值得留存的对话文本约 **2.6 MB**——**噪音占 95% 以上**。清洗后的归档约 1.7 MB。

这组数字说明了两件事：第一，直接全量导出是没用的（95% 是程序日志）；第二，清洗后体量很小，完全可以全文归档、全文检索。

## 二、已有方案与缺口

在动手之前，我们认真看过社区里几个同类项目，并且借用了它们最好的部分：

| 项目 | 我们借用了什么 |
|---|---|
| `Ar9av/obsidian-wiki` | 「编译而非堆积」的立场、声明式溯源标注、`.manifest.json` 增量台账 |
| `alvaroum/agents-vault-memory` | 会话 → 日 → 周 → 月 → 年的时间分层 |
| `broomva/control-metalayer` | 会话文档 + MOC 索引 + frontmatter 元数据 |

它们的共同点是：**通用**。通用意味着不假设数据源长什么样，于是只能靠启发式手段去猜——猜会话边界、猜标题、猜主题。

本项目的前提不同：**WorkBuddy 把结构都告诉我们了**。

- 会话边界不需要猜——`readdir` 就是，一个 jsonl 一个会话；
- 标题不需要猜——本地 SQLite 里就有（含用户自定义标题）；
- 工作目录不需要猜——jsonl 每行都带 `cwd`，会话表里也有；
- 时间不需要猜——每行都有毫秒时间戳。

所以本项目不需要「更聪明的算法」，只需要**把已有的确定性结构化利用起来**，然后把功夫花在**下游的图谱设计**上——这才是通用方案留给我们的真正空白。

需要说明的是：这不是「我们做得比它们好」，而是**换了一个前提**。前提变了，整个设计空间就变了。

## 三、主张一：编译，而非堆积

这是本项目最根本的一条，也是我们与「导出脚本」的分界线。

**堆积**是把原文搬到一个新位置：复制 jsonl、转成 markdown、塞进一个目录。你得到的是「同一堆东西换了个地方」，读起来依然困难。

**编译**是转换：解析 → 清洗 → 分类 → 建链 → 渲染成**给人读**的文档。产物不再是记录，而是**一篇有元数据、有导航、有出处标注的笔记**。

具体做了四件事：

1. **剥样板**：每条用户消息都被注入了 `system-reminder`、`project_context`、`user_info` 等大量平台样板。这些是给模型的，不是给你的。清洗阶段会反复剥掉（非贪婪正则、迭代 4 轮以处理嵌套），只留你真正写的那几句话。
2. **重组成轮次**：碎片的助手回复按「用户消息」分组拼接成完整的一轮，恢复对话的本来形状。
3. **降级标题**：归档正文里的 `#` 一律降一级（同时跳过代码块内的 `#`），避免污染 Obsidian 的大纲面板与图谱。
4. **写元数据与溯源**：产物带 frontmatter（主题 / 时间 / 人物 / 项目 / 状态 / 轮次…）与 `generated_by: ingest.py` 标记，既是可查询的结构化数据，也是「这文件是机器生成的、可被覆盖」的声明。

### 样例 A：一个会话归档长什么样

frontmatter 把三个维度写成了可查询的字段——`topic`（主题）、`timeline`（时间）、`person`（人物）：

```yaml
---
title: "给 FastAPI 服务加请求耗时日志"
type: conversation
topic: "工程与工具"
session_id: 0f3a1c2e-9b7d-4a51-8f6e-2d4c5b6a7e90
date: 2026-09-15
timeline: "2026-09"
person: "我"
started: "2026-09-15 10:20"
ended: "2026-09-15 10:52"
project: "Alpha 项目"
workspace: "d:\\projects\\alpha"
status: "finished"
turns: 2
tool_calls: 2
tags:
  - 对话归档
  - 工程与工具
generated_by: ingest.py
generated_at: "2026-09-17 00:45"
---
```

正文骨架 = 一个「会话档案」信息卡 + 克制的面包屑 + 分轮正文：

````markdown
# 给 FastAPI 服务加请求耗时日志

> [!info] 会话档案
> **时间**　2026-09-15 10:20 → 2026-09-15 10:52（32 分钟）
> **项目**　Alpha 项目　`d:\projects\alpha`
> **规模**　2 轮对话 · 2 次工具调用 · 状态 `finished`
> **主题**　[[工程与工具 总览|工程与工具]]

[[Home|← 首页]]　·　[[40-时间线/2026-09|← 2026-09 时间线]]

---

## 第 1 轮　`10:20`

**我**

> 服务里的慢请求排查不动，能不能在日志里带上每个请求的耗时？

**小迪**

可以在中间件里包一层计时，把耗时写进日志。

#### 实现                     ← 原文的 `###`，被整体降了一级

```python
@app.middleware("http")
async def timing(request, call_next):
    ...
```
````

注意两个细节，它们是刻意的：

- **面包屑只留两个出口**（首页、时间线月节点）。归档文件是最多的（一个会话一个），如果每个都链 3–4 个索引节点，边数会随会话数线性爆炸，图谱退化成一张毛球。语义出口只需要「从哪来回哪去」。
- **工具调用轨迹是可折叠的**，默认收起（`> [!example]-`）。它保留了「当时用什么手段解决了问题」的线索，但不占据阅读版面：

```markdown
> [!example]- 工具调用轨迹（2 次）
> - `Read` — {"file_path": "d:/projects/alpha/app/main.py"}
> - `Edit` — {"file_path": "d:/projects/alpha/app/main.py", ...}
```

## 四、主张二：四层职责分离

目录不是随便分的，每一层有明确的**写入权限**和**角色**：

| 层 | 目录 | 谁写 | 职责 |
|---|---|---|---|
| **索引层** | `00-总览/` | 脚本生成骨架，人可补充 | **只做导航，绝不写细节** |
| **知识层** | `10-主题/` | 人 | 结论、卡片、决策、跨主题关联 |
| **原料层** | `20-对话归档/` `30-我的记忆/` `30-人物/` `40-时间线/` | 脚本 | 忠实但经过清洗的记录（会话 / 记忆 / 人物 / 时间四种原料） |
| **原始层** | `90-原始数据/` | 脚本 | jsonl 只读副本，**不参与图谱** |

### 为什么「索引层只做导航」是一条硬规则

这是全项目最容易做错的地方，也是最容易让图谱变难看的地方。

直觉上，总览页应该列出「所有会话」，这样看起来才完整。但这样做会制造**大量无信息量的边**：总览 → 会话 A、总览 → 会话 B、…… 每条边都只是「我列了你」，不表达任何判断。图谱会变成一个星形辐射：一个中心点，外面挂着一圈点，点与点之间毫无关系。**这恰恰与知识图谱的目的相反。**

所以索引层的会话清单**不硬写链接**，而是交给 Obsidian 的 Bases 视图动态渲染：

```markdown
# 对话索引

> 会话总表由 **Bases 视图**动态生成 —— 不在这里硬写链接，
> 所以索引层不会在图谱里制造重复的连线。
> 想按主题看 → [[主题地图]]；想按时间轴看 → [[时间线]]。

共 **2** 个会话 · **6** 轮对话 · **11** 次工具调用

![[对话索引.base]]
```

配合的约定：总览页的列表**超过 5 行就拆成独立卡片**（而不是继续往下堆），同样是为了不让索引层长成第二个内容层。

### 三层信息的流动方向

```
原始层 (jsonl，不建边)
   ↓ 解析 + 清洗
原料层 (会话 / 记忆 / 人物 / 时间)
   ↓ 分类 + 聚合
知识层 (主题 → 主题)
   ↑
索引层 (只指路，不承载内容)
```

边只在有语义的方向上存在：会话 → 它所属的主题；会话 ↔ 它所在的月份；人物 → 他关注的主题；主题 → 相关主题。**没有「总览 → 每一个会话」这种边。**

## 五、主张三：图谱卫生是硬指标

多数「把笔记丢进 Obsidian」的方案止步于「文件生成了」。但生成文件和生成**一张能用的图**是两件事。我们把图谱质量变成可测量、可回归的指标，由 `check.py` 每次体检：

| 判据 | 目标 | 为什么 |
|---|---|---|
| **断链** | 0 | 断链在图上是一个悬空的点，读起来是「这里本该有东西」 |
| **零入链孤岛** | 0 | 孤岛节点在 Obsidian 里会飘在外面，永远走不到 |
| **`知识层 → 知识层` 边** | **越多越好** | 这是「网」与「辐射」的分水岭：主题之间互相引用，图才有结构 |
| **`会话 → 索引层` 边** | 越少越好 | 这类边只表示「被列出」，不含判断，是纯粹的噪音 |

**这四条判据里，后两条才是关键。** 前两条是「不出错」，后两条是「有价值」——一个只有前两条达标的库，可能是一堆互不相干的正确文件。

### 让孤岛自然消失：先有入链，再有节点

「孤岛 0」不是靠事后补链接达成的，而是靠**生成顺序**保证的：会话归档写入时链向主题总览与月节点；月节点汇总当月会话并链回主题；主题聚合页反查该主题下所有会话；人物节点链向关注过的主题。任何新会话一落地，它一定同时被至少一个上游引用。

这也是两条踩坑记录的来源：**时间线月节点的导航不能直接写「上月/下月」**（会链向不存在的月份），**人物节点的主题必须扫描全库而不是只取本批增量**（否则增量模式下人物节点只剩最近一批主题）。两者都是「为了让某个点不变成孤岛」而定的规则。

### 样例 B：时间线月节点与主题聚合页（知识层 ↔ 会话成网）

月节点显式列出当月会话，并链向本月涉及的主题：

```markdown
# 2026-09 时间线

> [!info] 本月共 2 个会话

## 会话

- [[20-对话归档/2026-09/2026-09-15-1020-给-FastAPI-服务加请求耗时日志|给 FastAPI 服务加请求耗时日志]]　`2026-09-15`
- [[20-对话归档/2026-09/2026-09-12-1405-把季度数据整理成-Excel-透视表|把季度数据整理成 Excel 透视表]]　`2026-09-12`

## 涉及的主题

- [[工程与工具 总览|工程与工具]]
- [[数据与报表 总览|数据与报表]]
```

主题聚合页是反过来的索引——从主题出发，回到它的全部会话（表格内的 alias 分隔符必须写成 `\|` 转义，否则会被解析成表格分隔符）：

```markdown
# 🛠️ 工程与工具 · 会话索引

> 本主题下共 **2** 个会话（由 ingest.py 自动聚合）。

| 日期 | 会话 | 项目 |
| --- | --- | --- |
| 2026-09-15 10:20 | [[20-对话归档/2026-09/2026-09-15-1020-给-FastAPI-服务加请求耗时日志\|给 FastAPI 服务加请求耗时日志]] | Alpha 项目 |
| 2026-09-12 14:05 | [[20-对话归档/2026-09/2026-09-12-1405-把季度数据整理成-Excel-透视表\|把季度数据整理成 Excel 透视表]] | 临时工作区 |
```

**实测结果**（一次全量试跑，45 个会话）：

```
节点 103　边 319　双链 459 处

【断链】23 条唯一目标
  x … -> [[双链]] / [[{t}]] / [[2026/08/xxx]] / [[{prev_month(month)}]] …
  （若出现在正文代码/示例里，可忽略）

【边的分层分布】
  会话     -> 索引层       51
  会话     -> 知识层       47
  会话     -> 时间线       45
  知识层    -> 会话        45
  时间线    -> 会话        45
  记忆/人物  -> 记忆/人物     41
  时间线    -> 知识层        8
  会话     -> 记忆/人物      7
  会话     -> 会话         6
  索引层    -> 知识层        5
  知识层    -> 知识层        5
  记忆/人物  -> 知识层        5
  …（以下为个位数）

【零入链（孤岛）】0 个
```

这份报告里有三点值得单独读：

1. **23 条「断链」全部来自对话正文本身**。因为在那些对话里我们讨论过双链写法，写下了 `[[双链]]`、`[[{t}]]`、`[[40-时间线/{prev_month}]]` 这类示意文本，归档时被原样保留。`check.py` 对此有专门的提示行。剔掉它们，**真实断链为 0**。
2. **「会话 → 索引层」51 条里，45 条是每个归档各一条「← 首页」**。这正是前面那条硬规则的量化体现：每个归档只保留两个语义出口（首页 + 所属月份），数量被压到每会话 1 条。若按常见的「面包屑串 3–4 个索引节点」做法，这一项会直接翻三倍——而那多出来的两条边，不表达任何判断。
3. **「知识层 → 知识层」只有 5 条**——诚实地说，这是当前最薄的一项。它来自自动生成的「主题总览 → 会话索引」聚合。这一项**不可能靠脚本堆出来**：它的密度取决于你往 `10-主题/` 里写了多少卡片、卡片之间互相引用了多少次。

第 3 点恰好把四层设计的边界画清楚了：**前两条判据（断链 0、孤岛 0）由脚本保证；后两条判据（边的质量）由使用习惯决定。** 脚本能保证的是一张「不出错的图」，能长成一张「有用的图」还要靠你往里写。

## 六、工程取舍与边界

### 取舍一：为什么用规则匹配，不用 LLM

主题分类是 `topics.json` 里的关键词规则（对「标题 + 工作目录」做包含判断，顺序匹配、先中者胜），不是语义理解。

放弃 LLM 换来四件东西：

| 得到 | 说明 |
|---|---|
| **确定性** | 同样的输入永远得到同样的分类，便于回归和 diff |
| **可离线 / 零依赖** | 只用 Python 标准库，不需要 API key，不产生费用，不联网 |
| **可测试** | 纯函数，35 个单测覆盖，CI 三版本矩阵跑绿 |
| **可审计** | 为什么这个会话被归到「工程与工具」？看 `rules` 就知道了 |

代价是：它不懂语义。标题里没有关键词的会话会落到 `default`。这个代价可以用**人工规则**补——加一条关键词，比调 prompt 便宜得多。真正需要语义理解时（例如「从对话里自动提取第三方人物」），再引入 LLM 也不迟：**先用确定性的方法把能做的做掉，把 LLM 留给它真正不可替代的地方。**

### 取舍二：幂等契约

重复运行必须安全，否则没人敢跑第二次。契约规定：

- 脚本只覆盖**自己生成的文件**——靠 frontmatter 里的 `generated_by: ingest.py` 标记识别；
- 绝不碰手工目录与手工内容，骨架文件若已存在就跳过（你可以在 `10-主题/* 总览.md` 里补卡片，重跑不会被清掉）；
- `.manifest.json` 记录每个会话的 `mtime`，第二次运行只处理新增/变更的会话（`--full` 可强制全量）。

增量带来一个必须警惕的陷阱，也已经踩过：**增量模式下，聚合类产物（人物节点、时间线月节点、主题聚合页）不能只汇总「本批新会话」**，否则内容会随着每次运行而缩水。它们必须扫描整个归档目录重新聚合。判断标准很简单——**产出物数量突然变少，就是这类 bug 的信号。**

### 取舍三：只读原则

工具**只读取** `~/.workbuddy/`，不改动任何原始数据（SQLite 也以 `mode=ro` 只读打开，不影响正在运行的 App）。这条原则的理由不是技术洁癖：

- 原始数据是唯一不可再生的资产——对话原文丢了就没了；
- 一旦工具可能写坏数据源，它就从「辅助」变成了「风险」；
- 只读让试错成本降到零：随便跑，跑坏了删掉 vault 重来即可。

同理，`30-我的记忆/` 下的身份文件与项目记忆都是**只读副本**，产物里显式写了警告：「不要改这里，改了下次同步会被覆盖。要改，改原件，然后重跑。」

### 已知局限

诚实列在这里，它们是「当前设计选择」而不是「待修的 bug」：

- **「人物」维度目前只有「我」一个节点**（从 `USER.md` 提炼），对话中提到的第三方人物尚未自动提取。这需要实体识别或 LLM——上面说过，那一步留给以后。
- **主题分类是关键词匹配**，不是语义理解。复杂语义靠人工调 `rules`。
- **增量判断依赖 jsonl 的 `mtime`**。外部工具若改了 mtime 会被误判为变更，代价只是多跑一次，无副作用。
- **孤儿文件风险**：`--no-*` 系列开关（如 `--no-person`）会跳过对应产物的生成，若之前生成过，旧文件会留在库里。手动删掉即可。

---

## 结语

一句话概括这套设计：

> **前提决定手段。** 因为 WorkBuddy 把结构留在了本地，所以可以放弃猜测、改用确定性解析；因为省下来的力气不该浪费在「更聪明的解析」上，所以把它花在产物形态与图谱质量上；因为图谱的价值在「边」而不在「点」，所以索引层被严格限制为只指路，知识层被要求互相关联。

如果你认同这个思路，欢迎看 [CONTRIBUTING.md](../CONTRIBUTING.md)；如果你只想先跑起来，回到 [README](../README.md)。
